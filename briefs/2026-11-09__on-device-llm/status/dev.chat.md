## Proposal: keys sent sealed to the device (for architect and security; not built)

Dinis (spoken, relayed by the conductor, 9 Nov about 13:25 UTC): a per-device secrets manager, with keys sent sealed to the device's own key over the team messaging lanes (WS-203) or by QR. The paste screen stays as the fallback. This is a design only; nothing here is implemented.

**Goal.** An OpenRouter key reaches a tablet without ever being typed, pasted in clear, or readable by whatever carries it (a chat lane, a QR image, a screenshot).

**1. The device key.** On first use of the import screen the app creates an EC P-256 key pair in the Android Keystore (non-exportable, purpose key agreement, alias `riskmandate_cloud_device_v1`). Only the public half leaves the Keystore. Key agreement in the Keystore needs API 31 or later; below that the screen offers the paste route only (the target tablet is far newer).
- The screen shows the public key as text and as a QR image (displaying a QR needs no permission), with a short fingerprint (the first 8 bytes of its SHA-256, in groups) and the device label. Staff read the fingerprint aloud or compare it on the sender's side. It is public data: it can be copied, sent, screenshotted.

**2. The sealed payload (a JSON file or one text line, `format: "riskmandate_sealed_key"`, `version: 1`).** Made by the sender (a small script run by whoever holds the OpenRouter account, outside the app): fresh ephemeral EC P-256 key; ECDH with the device public key; HKDF-SHA-256 (info = the format name, version and recipient fingerprint); AES-256-GCM with a random 12-byte IV, the associated data being the header below. Fields: `recipient_fp`, `ephemeral_public`, `iv`, `ciphertext`, `label` (the tablet's name, matching the key's label at OpenRouter), `issued_at`, `expires_at` (a short validity, for example 7 days), `nonce`, and an issuer `signature` over all of it.
- Only the holder of that tablet's Keystore key can open it. A payload for another tablet fails the fingerprint check before any decryption.

**3. Who may issue (the part security should decide).** Without a signature, anyone who learns a tablet's public key could send it a key from a different account, and the tablet's cloud prompts would then be billed to, and readable by, that account. So the payload carries an ECDSA P-256 signature by an issuer key. Options: (a) the issuer's public key is pinned in the app at build time (one more constant, revocable only with a new build); (b) staff pin it once on the tablet, in the same staff-only screen, by comparing its fingerprint (Trust On First Use, resettable). I lean to (b) with the fingerprint shown, because it needs no rebuild; security chooses.

**4. Import screen (Diagnostics, staff only, hidden in stand mode, FLAG_SECURE, same rules as the paste screen).** Paste the sealed text (it is not secret: the app may read what staff paste into its own field; there is still no clipboard read by the app) or, later, scan a QR. The app checks, in order: format and version, size bound, recipient fingerprint, signature, expiry, a nonce not seen before (the used nonces are kept in the cloud folder, bounded), then decrypts, checks the key's shape (`sk-or-` prefix, as `CloudKey.check`), stores it with `CloudKey.save` (the same Keystore-encrypted file as now) and calls `spend.initialise()`. The plain key exists only in memory during the import. The screen then says "key set" and shows the label; nothing about the key itself.
- Scanning a QR needs the CAMERA permission, which is a new permission and a security review item. Until then: paste only, or an Android share-to-app intent, which would be a new exported component (also a review item). I propose paste only for the first version.

**5. Rotation and revocation.** A new sealed payload replaces the stored key (same screen, same checks). Revocation stays at OpenRouter (each key is per tablet, labelled with the tablet's name, with its own credit limit); the app's Remove button deletes the local copy and the Keystore entry as now. A lost tablet: revoke that one key.

**6. What it does not give.** The sealed payload protects the key in transit and at rest. It does not protect against someone who can use the unlocked app or who has root; the paste screen has the same limit.

**7. Pieces and owners.** `cloud/SealedKey.kt` (parse, verify, open: pure Kotlin plus JCA, testable on the JVM with software keys, with the sender side as a test helper), the Keystore agreement key (device test), a small sender script (eval or release owns scripts; it must read the OpenRouter key from the environment, never an argument), the import UI (app). Tests: wrong recipient, tampered header, expired, replayed nonce, wrong issuer, bad shape, key never in an exception text, one device-test round trip.

**Questions for Dinis, architect and security.** (1) Issuer trust: pinned in the build or pinned once on the tablet? (2) Is paste-only acceptable for the first version, or is QR scanning (CAMERA) wanted at the stand? (3) Where does the sender script live and who holds the issuer private key? (4) The accountant's per-tablet budgets: should the sealed payload carry a spending hint (`limit_usd`) that the app shows but never enforces, since the real limit is the key's own credit limit?

**Security's decisions on this proposal (review of fb758ac, checklist M.8). They replace my open choices; nothing is built yet.**
- **Issuer: pinned in the build**, up to two public keys as constants, not trust-on-first-use (with TOFU the first person to show the tablet a payload becomes the issuer). The issuer private key is Dinis's alone, outside the repository and every agent.
- **Paste only first.** No CAMERA permission, no share-to-app intent, no exported component. A QR image needs an encoder library (a new dependency for security's review), so the device public key is shown as text first.
- **Sender script** with the scripts owner; the key comes from the environment or stdin, never an argument; only Dinis runs it with a real key.
- **Spending hint**, if any, sits inside the signed bytes, is shown as a hint, and never changes a cap.
- **Added requirements:** one canonical byte string for the signature and the AAD (not re-serialised JSON); compare the full SHA-256 of the device public key (8 bytes only for reading aloud); expiry a day or less; the nonce recorded after a successful import and kept until the payload's expiry, in a bounded store that refuses rather than forgets; delete the device agreement key after a successful import and on Remove key (a sealed payload left in a chat lane is a bearer secret while that key exists); strict JSON and base64 with a few-KB bound and fixed refusal messages; HKDF checked against the RFC 5869 vectors; the nonce store listed in the mandate view by exact name; test keys made in memory, no committed private key.
- **Caps (R-cloud-11, low):** Dinis writes the two numbers on the board; until then they stay US$1 a session and US$5 a tablet (the $1 is my inference from his $5). The credit limit on each key at OpenRouter remains the real backstop.
