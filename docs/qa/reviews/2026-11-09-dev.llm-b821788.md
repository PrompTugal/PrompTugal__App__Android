# QA review: the llm/ and feature G parts of dev b821788, as seen from the release build Dinis will have

Reviewer: qa.android@promptugal.ai · 9 Nov 2026 · Files: `llm/ModelFiles.kt` (`benchAvailable`), `features/models/ModelSetupScreen.kt`, `features/models/ModelSetupScreenTest.kt`; earlier reviews `2026-11-09-dev.llm-dc63ad8.md` and `-g-download.md` (Q-llm-1 LIFT, G download PASS)

Verdict: HOLD, for the device run: the planned flow cannot be followed on a release build. Two findings, both small fixes in dev.llm's files.

## Q-bench-1 (medium): a model downloaded in the app does not unhide the model bench on a release build
`ModelFiles.benchAvailable(context, debuggable = false)` is `debuggable || find(listOfNotNull(adbDir(context))).isNotEmpty()`: on a release build it looks **only at the adb folder**, but feature G installs into `noBackupFilesDir/models/` (the internal folder). Probe (`2026-11-09-dev.llm-b821788-benchgate.probe.kt.txt`): a catalogue file in the internal folder on a release build gives **bench offered = false**, so Diagnostics > Model bench stays hidden. The route to the bench on the Firebase build is therefore only an adb push, which Dinis said not to lead with, and the device guide's step 3 (bench after the in-app download) cannot be followed. Fix: `benchAvailable` should also be true when `find(listOf(internalDir(context)))` is not empty (keep the debuggable and adb conditions), with a test for the internal-folder case (the probe is that test). The staff-only intent (visitors on a stand tablet do not come across it) is kept, because the bench is still hidden when no model is installed and Diagnostics is already hidden in stand mode.

## Q-g-4 (medium, gate risk): `ModelSetupScreenTest.deletingThroughTheFeatureRefreshesTheHostsService` is flaky
It fails often: on plain `dev` b821788 in **2 of 5** isolated runs of `ModelSetupScreenTest` (`java.lang.AssertionError: no node tagged models_delete_gemma4e2b`), and it aborted two full-gate runs of the dev.lab merge in a row (and passed on the third). The test runs `host.refresh()` inside `runBlocking` on the main thread and then waits for the delete button with a real-time wait, so whether the screen's own load has finished depends on thread timing. Because a failing unit test stops Gradle before lint and the builds, every red of this kind blocks merges for nothing. Fix suggestion: wait for the state the screen reads (the host's `state` and the installed marker) with the looper idled between checks, the way `ModelBenchScreenTest.waitFor` does, and give `ModelSetupScreen` an injectable dispatcher as the bench already has (`io = Dispatchers.Unconfined` in tests). Until fixed, a lone red on this test is not a regression: re-run, or `--continue` to see the rest.

## Unchanged and fine
The pinned catalogue, the installer, the policy, the checksum and the probes from the earlier reviews; the privacy line now names "huggingface.co (and its download servers, hf.co)" (Q-g-1 adopted).
