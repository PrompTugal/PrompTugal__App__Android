## Findings

| ID | Severity | Where | Finding | Fix | Owner |
|---|---|---|---|---|---|
| R-rel-1 | Medium, before `main` is protected | `android.yml` job `security-approval` | It runs on `pull_request`, and for that event GitHub uses the workflow file from the pull request's own merge commit. A pull request that edits `android.yml` can rewrite or skip its own `security-approval` job, and a protection rule that requires the check by name would accept it. (`promote.yml` and `play.yml` are not affected: they run from `main`.) | Run it on `pull_request_target` (types opened, synchronize, reopened; branches `main`): that event uses the base branch's workflow file. Keep `ref: base.sha` and never check out or execute the head (the verifier reads it with `git` as data) | release |
| R-rel-2 | Medium, before `PLAY_SERVICE_ACCOUNT_JSON` is added | `play.yml` "Download the signed AAB", `find-release-tag.sh` | The AAB is tied to the approved commit by a tag name (`v<N>`, newest tag that is an ancestor with no build-path change) and a `SHA256SUMS` from the same release, which only catches corruption. Whoever can push a tag or edit a release can point `play.yml` at a different asset. Play's check that the AAB is signed by the upload key is the only other tie | Build provenance: in the release job add `attestations: write` (it already has `id-token: write`) and `actions/attest-build-provenance` (pinned by SHA) for the AAB and APK; in `play.yml` run `gh attestation verify <aab> --repo "$GITHUB_REPOSITORY" --source-digest <the dev commit the tag points at> --signer-workflow <repo>/.github/workflows/android.yml` (needs `gh`, in the runner) and fail closed | release |
| R-rel-3 | Low | `promote.yml` gate lookup | The `security-gate` result is read by check-run name only, so any workflow with `checks: write` could create one | Add `select(.app.slug == "github-actions")` to the jq filter | release |
| R-rel-4 | Low, a trust path gap in my code (fixed) | `approval-lib.mjs` `TRUST_PATHS` | The files that decide promotion and which build is uploaded (`scripts/promote-select.sh`, `scripts/find-release-tag.sh`, `scripts/changed-build-paths.sh`) were not trust paths, so a change to them could promote automatically on one PASS | I added them to `TRUST_PATHS` with a self-test case (16 cases pass). Copy the new `approval-lib.mjs` to `scripts/verify-approval-lib.mjs` unchanged | release (the copy) |
| R-rel-5 | Note | `docs/ci.md` | A promotion must be a fast-forward or a merge commit: a squash or rebase merge makes a new commit that does not descend from the approved head, so the verifier refuses it (and so does the human variant). Say so in the docs | One sentence in `docs/ci.md` | release |
