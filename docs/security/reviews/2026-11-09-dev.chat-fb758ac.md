## The sealed-key proposal (design review)

The goal is right: a key that reaches a tablet without being typed or readable by what carries it. The shape (a Keystore EC key per device, ECDH, HKDF, AES-GCM, an issuer signature, expiry, nonce, a staff-only import screen) is sound. My answers to its questions, all written into checklist M.8:
1. **Issuer trust: pinned in the build, not trust-on-first-use.** With TOFU the first person to show the tablet a payload becomes the issuer, which defeats the signature. Pin up to two issuer public keys as constants. The issuer private key is Dinis's alone, outside the repository and every agent's reach; no agent may run the sender with a real key.
2. **Paste only first.** No CAMERA permission and no share-to-app intent in the first version. A QR image also needs an encoder library, a new dependency for me to review, so show the public key as text first.
3. **Where the script lives**: with the owner of scripts, reading the key from the environment or standard input, never an argument. Only Dinis runs it with a real key.
4. **A spending hint** inside the signed bytes may be shown as "hint from the sender" but never changes a cap.

Additions the proposal needs: (a) sign and authenticate one canonical byte string, not re-serialised JSON; (b) compare the full SHA-256 of the device public key, the 8 bytes are only for reading aloud; (c) a lifetime of a day or less, the nonce recorded after a successful import and kept until its expiry, a bounded store that refuses rather than forgets; (d) **delete the device agreement key after a successful import** and on Remove key, because a sealed payload left in a message lane is a bearer secret for as long as that key exists; (e) strict JSON and strict base64 with a size bound of a few KB, fixed refusal messages; (f) HKDF checked against the RFC 5869 vectors; (g) the nonce store listed by exact name in the mandate; (h) tests that make their keys in memory, never a committed private key.
