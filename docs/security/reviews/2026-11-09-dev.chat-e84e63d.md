# Security review: work/dev.chat e84e63d (the cloud client, not wired to the host)

Verdict: PASS

Reviewed 9 Nov 2026 by security.android@promptugal.ai. Scope: `llm/cloud/` (`CloudEndpoint`, `CloudKey` with `KeystoreCipher`, `CloudTransport`, `CloudSpend`, `CloudLlmService`) and its tests, against checklist M. Nothing calls the client yet: no host wiring, no key screen, no consent switch, no badge, no policy text. The PASS is for merging this code as unwired; the conditions below must be met before it is wired, and I will review the wiring and the key screen as their own heads. The package is in `llm/cloud/` and `noBackupFilesDir/cloud`; architect's ruling is top-level `cloud/` and `feature_cloud`, and the conductor has asked for the move, which I will read afterwards. `KeystoreCipher` needs a check on a real device (Robolectric has no Keystore).

## Checks

| Check | Result |
|---|---|
| M.2.1 one pinned destination | PASS. `CHAT_URL` is a constant; `CloudEndpoint.isAllowed` requires lowercase `https://`, the host exactly `openrouter.ai`, no `@`, backslash, whitespace or control character, no `%` in the authority, port 443 only, and a path under `/api/v1/`; `HttpUrlTransport` checks it again; nothing can set the host at run time; tests use an injected transport |
| M.2.2 no redirects | PASS. `instanceFollowRedirects = false`; a 3xx is a failure with a fixed message; error bodies are never read; `Authorization` goes only in the request to the pinned URL |
| M.1.2 key storage | PASS in design. A 256-bit AES-GCM key generated inside the Android Keystore and never exported, a random 12-byte IV from the cipher on every write, ciphertext in a file written through a temporary file and renamed, in the no-backup folder; a damaged or unreadable file reads as "no key"; `clear()` deletes the file and the Keystore entry. JCA only, no new dependency |
| M.1.3 never shown or logged | PASS in design. The key is returned only through `withBearer` (internal, builds the header), never in `toString` ("CloudKey"), exceptions or errors (fixed phrases only: nothing from the request or the server reply is put in them); `scrub` removes the stored key and any `Bearer ...` text; tests check the key is absent from the body, the other headers, every error text and the encrypted file |
| M.5 spend | PASS in design. A check against a worst-case estimate before every request; the real cost from `usage.cost` recorded when the answer ends, also when it is stopped or cut off, and an estimate (list price times tokens, in whole micro-dollars) when the reply has none; a damaged spend file counts as "cap reached" (fail closed), a missing one as a fresh start; default cap US$1 |
| M.6 the reply | PASS. Streamed tokens are plain text; tool calls are only proposed (at most 8, name cut at 64, arguments under 8,192 characters before `checkToolCall`, which rejects above 4,096); a JSON or connection fault is a fixed error; a stop closes the connection |
| M.3 what is sent | PASS in the client. The body holds only the messages the caller gave, the model id, the settings and tools; `model` must be in the pinned list (three ids); no identifier, label or app data; `provider.data_collection = "deny"` is sent (OpenRouter's documentation lists `data_collection: "allow" or "deny"`, read 9 Nov 2026) |
| Isolation | PASS. `CloudIsolationTest`: only `HttpUrlTransport` touches `java.net`; no SDK, no permission, no manifest change |
| `scripts/secret-scan.sh` | clean |

## Findings

| # | Severity | Where | Finding | Fix | Owner |
|---|---|---|---|---|---|
| R-cloud-1 | Medium, before wiring (M.2.2) | `HttpUrlTransport` | No `User-Agent` is set, so `HttpsURLConnection` sends Android's default, which names the device model, Android version and build. That would go to OpenRouter on every request | Set a fixed `User-Agent` (for example `RiskMandate-Android`) in the transport and test it; set `useCaches = false` too | dev.chat |
| R-cloud-2 | Low | `CloudKey.check` | The paste check accepts any printable ASCII string of 16 to 256 characters; a different secret pasted by mistake (another provider's key, a password) would be stored and sent to openrouter.ai | Require the `sk-or-` prefix (M.1.4) and keep the length bounds | dev.chat |
| R-cloud-3 | Low | `CloudKey.last4()` | The screen may show the last four characters ("key ending in ab12"). M.1.3 said not even those. Four characters of a long key is a small disclosure and helps staff tell their keys apart | Dinis's choice; I accept it and change M to match, provided it is shown only on the staff-only key screen and never in logs, Copy run, the report or saved state | Dinis, dev.chat |
| R-cloud-4 | Medium, before wiring (M.5.1) | `CloudSpend.setCap`, `reset` | A function exists to raise the cap (up to US$100) and to set the counter back to zero. If a screen offers either to any staff member, the cap controls nothing a mistake or a bug can do | Keep `setCap` and `reset` out of any screen, or put them behind a deliberate, confirmed action on the staff-only key screen with a ceiling of a few dollars; the credit limit on the key itself is the real backstop (Dinis) | dev.chat, Dinis |
| R-cloud-5 | Low | `CloudLlmService`, one service per model | Two services (two models) can each pass the cap check and run together, so the total can overshoot the cap by one worst-case call each. M.3 says one request at a time | Share one gate (a process-wide lock or holder) between services, or make the host hand out one at a time | dev.chat |
| R-cloud-6 | Low | `HttpUrlTransport.MAX_BODY_CHARS`, `MAX_PROMPT_CHARS` | The reply may be 8,000,000 characters and the request 200,000 characters, where M.2.3 says 1 MB and 32 KB. A real answer is a few kilobytes (at most 2,048 tokens) and the spend cap bounds the request, so these are safe but loose | Lower the reply cap to 1 MB, and decide a request cap that fits the longest history Dinis wants to send; say so in M | dev.chat, security |
| R-cloud-7 | Low | `CloudKey.scrub` | It removes the stored key and `Bearer ...` text, not any other `sk-or-` string, which M.1.3 asks for | Add a pattern for `sk-or-` strings | dev.chat |
| R-cloud-8 | Info | memory | A key held in a Kotlin `String` cannot be zeroed; it lives in memory only while a request is built | Accept, and say so on the key screen with the Keystore line (M.1.2) | dev.chat |

R-cloud-1 and R-cloud-4 must close before the client is wired. None blocks merging unwired code.

## Summary

A small, careful client: one pinned host, no redirects, a Keystore-encrypted key that is never shown or logged, a spend cap that fails closed, fixed error text and tool calls only proposed. PASS to merge unwired. The User-Agent and the cap controls are the two items to fix first.
