# Architecture review: dev.lab b67a7c5 (feature I, ABP Lab on replayed samples), already merged on dev

Verdict: PASS (fix-forward findings below)

Reviewer: architect.android@promptugal.ai, 9 Nov 2026. Reviewed after merge (dev 5c27cee), read on origin/dev. Scope: `features/lab/` (AbpChecks, Scenario, LabRunner, LabPresets, LabScreen, NetworkReader, LabFeature), `feature_lab.xml` (en, pt-PT), tests. `enabled = false`.

## What is good
- **The model proposes, code decides:** `AbpChecks` is one pure Kotlin module (no Android type, network, file or intent), with ordered checks (unknown tool, bad arguments, out of mandate, read-only, egress destination, egress secret), claim checks against the triplets actually fetched, and masked secrets in what the screen shows. It has unit tests (`AbpChecksTest`), as the brief asks.
- **Tools are fakes:** `FakeTools` only records calls and reads the scenario's demo graph. A new `FakeTools` per run; no shared state. The raw path runs every call on the fakes, and the ABP path stops denied calls before they run. `LabRunner` is pure and tested (`LabRunnerTest`).
- **Honest presets:** `LabPresets` are hand-written samples marked `sample = true`, and the screen says so. Synthetic secret and planted instruction, shown as text.
- **Structure:** content only, inside `ui/FeatureContent`, no own frame. The scenario choice is `rememberSaveable`; the replay animation is a `LaunchedEffect` that respects reduce-motion. `NetworkReader` uses the already-held `ACCESS_NETWORK_STATE`, read-only. Strings per feature, en and pt-PT. No new dependency. No global mutable state (the `object`s hold only `val` data).

## Findings for dev.lab (fix forward)
- **A-lab-1 (medium):** argument validation checks only **extra** arguments. The README rule (On-device LLM, tool calls) is: unknown name, missing, extra, wrongly typed or oversize argument → rejected. Add missing required arguments and a length cap per argument (and a total), with tests, before live model output reaches `checkCall`.
- **A-lab-2 (medium, shared with eval A-eval-2):** the ABP checks exist twice, in Kotlin here and in Python in `eval/abpeval/abp.py`, with different rule vocabularies (no `hold` here). The tablet's loop export is re-scored by the Python oracle, so a silent difference becomes a wrong number on stage. Run eval's golden check vectors (one JSON file owned by eval) in `AbpChecksTest`, and align the names.
- **A-lab-3 (medium):** scenarios are Kotlin constants and recordings are `Turn` lists, while eval owns `abp-eval-scenario/1` and `abp-lab-recording/1` (an event list with `t_ms`). Before curated recordings land, add a small parser (`org.json`, no new dependency) for both formats into these same types, bundle the demo subset under `app/src/main/assets/feature_lab/`, and record the scenario `hash` the app ran (the loop export needs it). Keep the Kotlin constants only as test fixtures.
- **A-lab-4 (low, for live mode):** binding to `LlmService` (when `FeatureContext.llm` lands): map each `ToolCallProposed(name, argsJson)` to `ToolCall` through one parser that rejects non-flat or non-string values (that rejection is itself an event the screen shows). Claims come from the model's text through the same claim protocol as eval's `claims.py`; agree it with eval rather than inventing a second one. One loaded model, the two paths interleaved (the service serialises).
- **A-lab-5 (low):** `claimsRemote` is a word-list heuristic (`"api"` will also match words like "rapid"). Fine as a flag, but label scenario 5 as a heuristic on screen, as eval does, and match on word boundaries.
- **A-lab-6 (info):** `task` and `document` are English in both languages. Correct for model input; if they are shown to visitors, show a pt-PT gloss from resources beside them.
