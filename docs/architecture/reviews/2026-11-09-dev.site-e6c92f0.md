# Architecture review: work/dev.site at e6c92f0

Verdict: HOLD

Reviewer: architect.android@promptugal.ai, 9 Nov 2026. Scope: `features/site/`, `res/raw/site_*.html`, `feature_site.xml`, tests. WebView details are security's to PASS as well (`docs/security/summit-checklist.md` A); this review covers structure, lifecycle and coupling.

Trial merge (dev + architect + app f317cf8 + qa + design + stand + abpdemo + mandate + site): **site does not compile** against FeatureContext v2. With that patched locally, 3 of qa's static tests fail on site files (2 of them are qa false positives, see qa review A-qa-6, A-qa-7).

## What is good
- The URL decision (`SitePolicy`) and the offline mode (`OfflineSwitch`) are pure and JVM-tested. Main-frame navigation off the allow-list never loads (`shouldOverrideUrlLoading` returns true). Sub-resources to any other host are blocked in `shouldInterceptRequest`. Frames cannot take the visitor away.
- Settings follow checklist A2 and A3: no JS bridge, no file or content access, mixed content never, Safe Browsing on, no multiple windows, no third-party cookies, DOM storage off. No `WebChromeClient`, so permission prompts are denied by default; no `DownloadListener`; debugging not enabled.
- Lifecycle: `AndroidView(onRelease = { stopLoading(); destroy() })`. The client holds the application context.
- The bundled pages have no external `<script src>`. Their off-site links are refused, not opened (`Browser.open` refuses anything that fails `Links.isAllowed`), so nothing escapes stand pinning.

## Findings for dev.site
- **A-site-1 (HOLD, compile):** `Browser.isOffline(context.activity)`: v2 has no `activity` (architect e3eb80c, app f317cf8). Use `val ctx = LocalContext.current; remember { OfflineSwitch(Browser.isOffline(ctx)) }`.
- **A-site-2 (HOLD):** `SiteScreen` draws its own Back button, title and `safeDrawingPadding` inside the host's `FeatureFrame`: two Back buttons, two titles, insets twice. Keep only the tab row, the offline banner, the message and the WebView. Drop `feature_site_back*` and the `SiteTags.BACK` tests.
- **A-site-3 (medium):** no `onRenderProcessGone`. If the WebView renderer dies (common on low-memory tablets, or when a stand tablet runs for hours), the whole app is killed. Override it: return true, drop the WebView (bump a key so `AndroidView` recreates it), and show a native message.
- **A-site-4 (medium):** the offline copy is served under the real `https://riskmandate.ai/` origin through `shouldInterceptRequest` from `res/raw`. My rules and checklist A2 ask for `WebViewAssetLoader` on `appassets.androidplatform.net`. This approach keeps the allow-list unchanged and the links working, which is a reasonable trade, but it is security's call: the offline pages run with riskmandate.ai's origin and can read its first-party cookies. Get security's explicit OK in their review, or switch. Either is acceptable to architecture.
- **A-site-5 (low):** `tabIndex` and `loadKey` are `remember`, not `rememberSaveable`. A tablet turn recreates the Activity and drops the visitor back on the Home tab. Save `tabIndex` (an Int).
- **A-site-6 (low):** `Decision.EXTERNAL` and `openExternal` read as "opens the browser", but every EXTERNAL URL fails `Links.isAllowed`, so `Browser.open` always refuses. Name it `REFUSED` and show the refusal message directly, so nobody later "fixes" it into a real escape from stand mode.
- **A-site-7 (low):** to satisfy qa's static checks without weakening them, call `SitePolicy` (which calls `Links.isAllowed`) in `SiteScreen` and `SiteWebView`; qa will accept the delegate (A-qa-7). Strings mix the `feature_site_` and `site_` prefixes: use `site_` for all.
- **For mandate (A-man-4):** this WebView keeps first-party cookies and an HTTP cache under `app_webview/` and `cache/`. Mandate's reach view must count them, and the "app collects nothing" sentence stays true only with the conductor's wording (riskmandate.ai's own privacy policy applies to the pages).
